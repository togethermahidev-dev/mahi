# Mahi staff portal (`staff/`)

A small website, for Mahi staff only, to work through reports: see what was reported, who reported
it and the person's history, and then dismiss it, hide a post, remove a comment, warn, suspend or
(admins) ban. Everything it does goes through the staff calls in `docs/moderation.md`, which is the
contract; every action needs a note and is written to the audit log by the database.

Pages: **Reports** (filter by status, what was reported and reason), a report's page (the content
as it was when reported, the automatic check's result, the person's warnings and bans, other
reports, what staff did, and the action buttons), **People** (search; everyone suspended or banned
now; one person's standing) and **Audit log**.

## Run it on your computer

From the repo root:

```sh
pnpm install                          # once, or after pulling new packages
cp staff/.env.example staff/.env.local  # then paste the anon key into it
pnpm dev:staff                        # http://localhost:3001
pnpm build:staff                      # a production build
pnpm lint:staff                       # design-token check + ESLint
pnpm test:staff                       # the staff-role and action rules
```

It talks to the real (production) database, because Mahi has only one. Signing in and looking is
harmless; **every action button changes real people's accounts**.

## Who can get in

Only accounts listed in `staff_users`. Sign-in is an ordinary Mahi email and password; the server
then asks the database `my_staff_role()`. Anyone not on the list is signed straight back out and
never gets past the sign-in page. Every page checks again on the server, and the database refuses
every staff call from non-staff anyway.

| Role | Can |
| --- | --- |
| Moderator | Everything except ban and unban |
| Admin | Everything |

### Add a staff member (owner)

They need a normal Mahi account first. Then, in a **new migration** (never the dashboard):

```sql
insert into public.staff_users (user_id, role) values ('<their user id>', 'moderator');  -- or 'admin'
```

…and push it the usual way (`scripts/db.sh backup`, then `scripts/db.sh push`). To remove someone,
a new migration that deletes their row. Their next page load signs them out.

## How it's built

- Next.js, server-rendered (not a static export like `web/`). Design values come only from the
  app's tokens through `web/app/tokens.css` (generated by `web/scripts/build-tokens.mjs`); the same
  check (`web/scripts/check-tokens.mjs`) runs on `staff/app` and `staff/components`. Inter only.
- Supabase is used **only on the server**: the browser holds two httpOnly cookies (the staff
  member's own session) and never sees a key. Only the public anon key is used; there is no
  service-role key and there must never be one in this app.
- `proxy.ts` refreshes the session; `lib/staff.ts` is the staff check every page runs;
  `lib/guard.ts` holds the role rules and `lib/rpc.ts` maps each button to its staff call (both
  tested in `lib/*.test.ts`).

## Deploying (owner only)

Not deployed anywhere yet. It needs a host that runs Next.js on a server (Vercel, or Netlify with
its Next.js runtime) — it can't be a static upload. Settings for the host:

- Base directory `staff`, build command `pnpm --filter ./staff build` from the repo root.
- Environment variables `SUPABASE_URL` and `SUPABASE_ANON_KEY` (the same public values the app uses).
- Put it on its own address (for example `staff.mahitechnology.com`) and, if the host allows,
  behind its password or single sign-on as well.

Before the first deploy the moderation migration (`20261006100000_moderation`) must be live and you
must be in `staff_users`; see the owner steps in `docs/moderation.md`.
